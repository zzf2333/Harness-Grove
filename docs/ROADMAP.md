# 产品开发路线（ROADMAP）

**状态：** 2026-10-31 定稿的**唯一产品开发总计划**。产品契约（边界、术语、生命周期、评估口径）在 [PHE_SPEC](PHE_SPEC.md)；各阶段已交付的证据留在各自的 `M*_PLAN.md`。本文与 SPEC 冲突时，产品边界按 SPEC，排程和完成状态按本文。

**本版依据（2026-10-31 用户澄清，最高产品依据）：**

- PHE 是面向所有用户的开源产品，不是开发者私人配置管理工具。项目测试与验收默认用隔离沙箱，独立可复现，不依赖开发者电脑的真实配置。
- 用户安装后，结合自己已有的完整 Agent Harness、行为习惯、思考与使用方式和会话反馈，持续个性化优化，帮助驾驭 Agent，目标是越用越好。
- 不是仅配置管理器，不是评测框架，也不扩成人格画像。资产管理是基础，评测是手段；效果按证据区分未知。

**重排原因：** 旧排程把评测能力和沙箱样例当成了产品完成（M1 只到沙箱、M2 只到历史采集、M3a 只到草稿检查），而真正的产品主线——用户如何开始用、如何覆盖完整 Harness 资产、如何跨周期累积——没有排进去。本版把主线写成 R1–R4，历史阶段只作为证据和契约来源。

**事实与规划的标记：** 本文标为“已实现/验证”的只指当前代码与已有证据；“未支持”是缺口。R1–R4 是排程。已交付：R1 的初始化与只读发现入口（沙箱验收，[acceptance/r1.md](acceptance/r1.md)）、R2 的产品入口（文件层验收，[acceptance/r2.md](acceptance/r2.md)）、R3a 的 Skills 文件层闭环与一次隔离 Host 的发现/显式展开（[acceptance/r3a.md](acceptance/r3a.md)）、R3b 第一片的 MCP 条目级更新（[acceptance/r3b.md](acceptance/r3b.md)）。仍缺：安装包与默认 `~/.phe`、真实 Host 加载验证、R3b 的新增/删除与 Codex、R3c–R3e、R4，以及模型自主选用与收益证据。

## 1. 产品目标

用户得到的结果：

1. 装好之后能看清自己机器上实际生效的 Harness：有哪些指令、Skills、MCP、Hooks、扩展和工具配置，来自哪里，哪个 Host 入口在读，PHE 能管到哪一步。
2. 用自己的会话反馈、明确偏好和现有配置，得到带证据和实际 diff 的建议；逐条批准后才生效，每次改动可追溯、可恢复。
3. 下次复盘对照原预测，判断保留、调整还是撤销；新证据继续累积，同一个资产越用越贴合自己的习惯。
4. 换模型、改工具、Host 升级、偏好变化之后，仍能维护这套配置，而不是从零重来。

不是这些：不是配置管理器（只管集中存放）、不是评测框架（只跑对照实验）、不是开发者个人配置的托管脚本。

## 3. 完整 Harness 资产：逻辑类型与物理存储

**逻辑资产类型**回答"这是哪一类 Harness 资产"：指令、Skill、MCP 服务器条目、Hook、扩展/插件/子代理定义、工具与权限配置。**物理存储**回答"它放在 PHE_HOME 的哪个位置"：`assets/<asset_id>/`，`asset_id` 是 `asset-0001` 起的高水位编号。一个逻辑资产被多个 Host 入口共享时，只有一个 `asset_id`，多个入口指向同一个发布。

当前实现的物理布局（沙箱已验证，不是"第二套设计"）：

```text
<PHE_HOME>/
  assets/<asset_id>/content/      # 逻辑资产内容；asset.json 记 asset_id / kind / name / source / imported_at
  assets/<asset_id>/asset.json
  releases/rNNNN/                 # 不可变发布；manifest.json 记每个文件的 sha256、size、asset_id
  releases/rNNNN/files/<asset_id>/
  releases/high_water.json        # 发布编号高水位，不复用
  bindings.json                   # agent -> { 入口路径: release }
  ledger.jsonl                    # 只追加的 approval / apply / restore / review 事实（change.py）
  journal/                        # 每次 deploy 的旧状态记录，供 rollback/restore
  staging/                        # apply 的暂存目录
```

`tools/release*.py` 的 `--home` / `--phe-home` 都必填，且拒绝等于真实 home、它的祖先或落在 `~/.claude`、`~/.codex`、`~/.pi`、`~/.phe`、`~/.agents`、`~/AI/temper` 之内的路径。开发期没有"默认帮用户选中真实环境"的行为。

**发现覆盖（R1，已交付）：** `tools/workspace.py discover` 把上表能盘点的类型逐条列进 `<PHE_HOME>/reports/discovery.{md,json}`，并给每类一个管理状态：`沙箱可托管`（指令）、`部分可托管`（Skills、MCP 的已存在条目）、`仅观察`（工具配置、扩展/插件/prompts、规则与记忆目录）、`未支持`（Hooks，无候选路径，报告不猜路径）。每类都有“发现 N 条 / 未发现 / 未支持”三态，项目级范围只在传了 `--project` 时扫描，没传时报告写“未扫描”。每条记录带 `load_chain unverified`：这一列不证明任何配置被 Host 加载过。

## 4. 证据口径

**三类信息分开标注，不能混用：**

- **用户明确偏好：** 来源是用户原话（带时间与位置），适用范围内有效；偏好变化时旧条目按“被替代”处理，保留历史与理由，不静默改写。偏好只描述用户明说的要求，不据此推断人格、性格或心理画像。
- **会话观察：** 来源是会话源文件指针；适用范围是该会话/项目，推广到别处需要新证据。
- **假设：** 有观察依据（具体证据指针）但预期改善未验证，标"收益待验证"，不写成事实；文章和外部资料只是假设来源，本身不构成观察依据。

**来源与适用范围可修正：** 路径、时间、Host 与版本进入账本或报告；来源失效、Host 升级或依赖变化时标 `needs_review`，不沿用旧结论。

**不算改善证据的东西：** 用户批准、apply 成功、文件被写入、Host 没报错、"没人报问题"、检索没命中（`unavailable` 不等于 `no_match`，没命中也不等于问题不存在）。没有证据时复盘记 `observe` / `prediction_met=unknown`。

**评估层次沿用 SPEC §2.5：**

- **L1（改动生效）** 在沙箱完成，应用、加载、恢复分开记：应用成功只说明字节或链接变了；被加载要在隔离 Host 里确认；恢复要回到应用前字节。任一层没做就写未验证，不用"改动生效"一句带过。
- **L2（隔离 Host 对照）** 是可选手段，按费用与已有授权判断，只在用户点名、改动有争议或改错后果严重时做；它不等于加载验证。
- **L3（用户自己观察）** 是用户自愿的日常观察，不是项目测试，不强制隔离环境或预算；前后对比只说明相关，不证明因果。

加载/触发验证是在一次性隔离 Host 里确认配置被读取或资产被触发，本身不等于 L2 对照，也不必按对照实验计费和审批。本轮不运行 Host，也不把"还没跑 L2"写成"已验证"或"不可验证"。

## 5. 路线

四片按用户能感知的结果切分，不按技术层。每片自己端到端验收，不存在"最后统一集成"阶段。

### R1 独立开始使用

**用户场景：** 一个不是作者的用户在另一台机器上把仓库 clone 到任意目录，按文档在一个隔离目录里初始化自己的 PHE_HOME，看到"我有哪些 Harness 资产、来自哪个文件/软链、哪个 Host 入口在读、PHE 能管到哪一步"的发现报告。全程不改动他的 Host 配置。

**复用：** `tools/inventory.py`（候选路径表与分组）；`tools/registry.py` 的 `adopt`/`drift`；`release_deploy.py` 的守卫与 `sandbox_roots`；`tools/history_hosts.py` 的 Host 根解析；`examples/lightweight-loop` 的"每步命令 + 临时目录"写法。

**现状（2026-10-31）：** 已交付 `tools/workspace.py`，两个子命令：`init --phe-home <目录>`（建目录骨架与格式版本标记，重复运行保留数据，版本不符时拒绝）；`discover --phe-home <目录> --home <显式 Host 根> [--project <根> …] [--registry <登记表>]`（复用 `inventory` 的候选路径表做只读盘点，读登记表给登记状态，写 `<PHE_HOME>/reports/discovery.md|json`）。克隆后从任意工作目录用 `python3 -I <源码>/tools/workspace.py` 运行，不读真实 home。首次使用流程在 [README](../README.md)，验收证据在 [acceptance/r1.md](acceptance/r1.md)。

**缺口与交付物：**

1. 初始化入口：创建/校验 PHE_HOME（目录骨架 + 版本标记），默认路径只在显式参数或环境变量下生效，不自动创建。—— 已交付：`init` 建 `assets/`、`releases/`、`workspace.json`；`--phe-home` 与 `PHE_HOME` 都没有时退出 2，`~/.phe` 不会被创建。
2. 发现报告：每类资产的来源路径、Host 入口、管理状态（可托管 / 仅观察 / 未支持）、加载链如实标 `unverified`。—— 已交付：四档管理状态（`沙箱可托管` / `部分可托管` / `仅观察` / `未支持`）+ 每类“发现 N 条 / 未发现 / 未支持”，每条带 `load_chain unverified`。
3. 安装不依赖源码工作目录：入口能从仓库副本或安装目录运行，输出里没有开发者绝对路径。—— 已交付到“克隆后任目录运行”：不依赖 cwd、不读仓库内状态、代码里没有固定绝对路径；**安装包与默认路径仍未提供**。
4. 一份按文档可跑通的全流程，所有写入落在显式沙箱。—— 已交付：README「克隆后开始使用」全用合成 Host，产物只在临时目录。
5. 产物落点：发现报告与测试数据写到显式指定的仓库外目录（临时测试数据目录或 PHE_HOME），替换开发期写在仓库内被 Git 忽略目录里的 legacy 做法。—— 发现报告已落在 `<PHE_HOME>/reports/`；摘要与复盘报告仍在仓库内 `episodes/`、`reports/`，属 R2 待办。

**验收结果（2026-10-31，全部在临时目录，证据与命令见 [acceptance/r1.md](acceptance/r1.md)）：**

- 全新临时目录 + 仓库副本（不是开发工作目录）跑完整流程，`--home` 指向合成 Host 树，退出码 0。—— 验收脚本与 `tests/test_workspace.py` 均 exit 0。
- 发现报告覆盖 §3 的资产类型，每类都有管理状态；未知项不被写成"已支持"。—— 覆盖摘要 10 行（含 Hooks 一行“未支持”），MCP 只写文件级观察，Skills 只写发布/部署能力。
- 同一 fixture 两次运行输出一致（可复现）。—— `discovery.md` 与 `discovery.json` 两次字节相同（`tests/test_workspace.py` 断言）。
- 隔离 fixture 里的已托管与未托管输入在运行前后不变：文件、目录与软链目标的字节和指向都与运行前一致；所有输出只落在显式指定的测试数据目录。—— 前后快照对比后新增路径只有 `phe/reports/` 下的三个路径。
- 不为证明隔离去读取或比较开发者本机的 `~/.pi`、`~/.codex`、`~/.claude`、`~/.phe` 等目录。—— `tools/workspace.py` 不引用 `Path.home()`，只读 `--home`/`--project` 与 `<PHE_HOME>` 下的报告/登记表。
- 新增的提交工件里没有本机用户名和真实路径（历史工件的本机路径见 §2，另行处理）。—— 新增文件只有 `tools/workspace.py`、`tests/test_workspace.py`、文档与验收记录，验收记录里的路径归一化为 `$WORK`。

**仍未验证：** Host 是否真的加载或触发这些配置（每条都是 `load_chain unverified`，需一次性隔离 Host 验证，不属于 R1 验收）；安装包与默认 PHE_HOME（产品规划，未实现）；MCP 条目级语义、Hooks、工具配置的值级模型（R3）。

**依赖：** 无前置。与 R2/R3 共享契约：ObservedAsset 字段、`kind` 取值、PHE_HOME 目录骨架。

### R4 多用户、多周期可持续维护

**用户场景：** 一个用户有两台机器（或两个用户各一台），各自 PHE_HOME；几个月后框架升级、偏好变了、Host 目录被手改。用户要的是"继续用，而不是推倒重来"。

**现状：** 账本、发布、绑定都在单个 PHE_HOME 下；没有跨实例隔离测试；没有框架升级兼容策略；外部变更只在 deploy 时中止并报告。

**缺口与交付物：**

1. 实例隔离：同机两个 PHE_HOME 互不读写（第二个用户用隔离的合成实例代表）；账本不把别人的绝对路径当永久证据。
2. 跨周期维护：新证据累积；偏好变化用"替代"而非静默改写；外部手改后用户选 `adopt / reconcile / leave_unmanaged`；框架升级后旧账本与绑定可读，或给出明确的兼容失败。
3. 退役与重开：Retired 账本，reopen 需要退役之后的新证据或用户显式授权。
4. 周期复盘视图：这轮改了什么、证据到哪、下次看什么。

**验收：** 同一台机器上两个合成用户的隔离实例（两个临时 PHE_HOME + 各自的临时 home）互不影响（账本、发布、绑定）；连续合成使用周期里，第二周期能引用第一周期的证据与结论；一次合成升级 fixture 里，旧版本账本被新版本读取并给出明确结果，不静默忽略；外部手改后 deploy 中止不覆盖，用户选择后继续；偏好被替代时保留历史与理由，不复用旧证据冒充新验证；产出一份合成周期复盘，含 `observe`/`unknown` 项。

**依赖：** R1–R3 的布局与账本；隔离核对可以先做，不依赖 R3 完成。

**完成 / 停止：** 上述验收在两个合成用户实例 + 连续合成周期 + 一次升级 fixture 上成立即完成，不要求第二台真实机器、第二个真实用户或真实时间周期的复盘。真实日常使用中的效果观察另列可选后续，不计入完成条件。

## 7. 完成口径与不做的事

- **完成状态必须带范围：** 写清哪一步在哪个环境验证过——文件层（沙箱字节/链接）、加载层（隔离 Host 确认被加载/触发）、行为层（观察窗或对照）。"沙箱通过"不等于"Host 已加载"，"Host 已加载"不等于"行为改善"。
- **沙箱是正常验收方式，不是临时妥协：** 项目测试、示例和每片验收都在临时目录里独立复现，不需要开发者电脑上的真实配置。涉及加载/触发的结论在一次性隔离 Host 里验证，同样不依赖开发者日常环境。L1 的应用、加载、恢复分开记；L2 对照按费用与授权可选；L3 用户自愿的日常观察不是项目测试，不要求隔离或预算。
- **"接管开发者本机现有配置"（包括 temper 迁移）不是里程碑**，只是用户批准后可选执行的一次迁移任务，不进入任何 R 片的完成条件。
- **不加防御性工程任务：** 按 AGENTS.md 铁律，畸形输入、攻击防护、并发锁不列为交付项；出现时只记一行后续事项。
- **不做的产品扩展：** 不造 Agent/运行时，不做人格画像，不做评测平台化，不扩成软件包管理器，不建第二套任务账本或第二套资产布局。
