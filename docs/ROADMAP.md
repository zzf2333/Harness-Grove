# 产品开发路线（ROADMAP）

**状态：** 2026-10-31 定稿的**唯一产品开发总计划**。产品契约（边界、术语、生命周期、评估口径）在 [PHE_SPEC](PHE_SPEC.md)；各阶段已交付的证据留在各自的 `M*_PLAN.md`。本文与 SPEC 冲突时，产品边界按 SPEC，排程和完成状态按本文。

**本版依据（2026-10-31 用户澄清，最高产品依据）：**

- PHE 是面向所有用户的开源产品，不是开发者私人配置管理工具。项目测试与验收默认用隔离沙箱，独立可复现，不依赖开发者电脑的真实配置。
- 用户安装后，结合自己已有的完整 Agent Harness、行为习惯、思考与使用方式和会话反馈，持续个性化优化，帮助驾驭 Agent，目标是越用越好。
- 不是仅配置管理器，不是评测框架，也不扩成人格画像。资产管理是基础，评测是手段；效果按证据区分未知。

**重排原因：** 旧排程把评测能力和沙箱样例当成了产品完成（M1 只到沙箱、M2 只到历史采集、M3a 只到草稿检查），而真正的产品主线——用户如何开始用、如何覆盖完整 Harness 资产、如何跨周期累积——没有排进去。本版把主线写成 R1–R4，历史阶段只作为证据和契约来源。

**事实与规划的标记：** 本文标为“已实现/验证”的只指当前代码与已有证据；“未支持”是缺口；R1–R4 全部是规划，**没有一项已经实现**，也没有安装/初始化入口、真实配置写入或 Host 加载验证。

---

## 1. 产品目标

用户得到的结果：

1. 装好之后能看清自己机器上实际生效的 Harness：有哪些指令、Skills、MCP、Hooks、扩展和工具配置，来自哪里，哪个 Host 入口在读，PHE 能管到哪一步。
2. 用自己的会话反馈、明确偏好和现有配置，得到带证据和实际 diff 的建议；逐条批准后才生效，每次改动可追溯、可恢复。
3. 下次复盘对照原预测，判断保留、调整还是撤销；新证据继续累积，同一个资产越用越贴合自己的习惯。
4. 换模型、改工具、Host 升级、偏好变化之后，仍能维护这套配置，而不是从零重来。

不是这些：不是配置管理器（只管集中存放）、不是评测框架（只跑对照实验）、不是开发者个人配置的托管脚本。

## 2. 三个空间与数据归属

| 空间 | 内容 | 归属与边界 | 当前状态 |
|---|---|---|---|
| 开源源码仓库（本仓库） | 代码（`tools/`）、Skill（`skill/`）、测试（`tests/`）、文档、手写合成示例（`examples/`） | 公开仓库；不含任何用户的会话、真实配置或个人路径；测试 fixture 全部手写合成 | 已存在 |
| 每用户 PHE_HOME | 资产源、不可变发布、绑定、账本、暂存与 journal | 归用户，在仓库外；产品规划默认 `~/.phe`，**只是规划** | 无安装/初始化入口，也没有默认路径；所有写入靠显式 `--phe-home` |
| 用户 Host 入口 | `~/.pi`、`~/.codex`、`~/.claude`、`~/.agents` 及项目级目录里实际生效的文件与链接 | 归用户；PHE 只在部署时改这些入口，且须用户按具体 diff、目标路径和恢复方式批准 | 只读盘点已实现；写入只在沙箱演练过 |

开发与验收使用显式隔离目录（临时 home + 临时 PHE_HOME），不依赖上面任何真实路径。会话历史不复制进仓库：只保存源文件指针与脱敏摘要，产物落在被 Git 忽略的 `episodes/`、`reports/`。

## 3. 完整 Harness 资产：逻辑类型与物理存储

**逻辑资产类型**回答"这是哪一类 Harness 资产"：指令、Skill、MCP 服务器条目、Hook、扩展/插件/子代理定义、工具与权限配置。**物理存储**回答"它放在 PHE_HOME 的哪个位置"：`assets/<asset_id>/`，`asset_id` 是 `asset-0001` 起的高水位编号。一个逻辑资产被多个 Host 入口共享时，只有一个 `asset_id`，多个入口指向同一个发布。

当前实现的物理布局（沙箱已验证，不是"第二套设计"）：

```text
<PHE_HOME>/
  assets/<asset_id>/content/      # 逻辑资产内容；asset.json 记 asset_id / kind / name / source / imported_at
  assets/<asset_id>/asset.json
  releases/rNNNN/                 # 不可变发布；manifest.json 记每个文件的 sha256、size、asset_id
  releases/rNNNN/files/<asset_id>/
  releases/high_water.json        # 发布编号高水位，不复用
  bindings.json                   # agent -> { 入口路径: release }
  ledger.jsonl                    # 只追加的 approval / apply / restore / review 事实（change.py）
  journal/                        # 每次 deploy 的旧状态记录，供 rollback/restore
  staging/                        # apply 的暂存目录
```

`tools/release*.py` 的 `--home` / `--phe-home` 都必填，且拒绝等于真实 home、它的祖先或落在 `~/.claude`、`~/.codex`、`~/.pi`、`~/.phe`、`~/.agents`、`~/AI/temper` 之内的路径。开发期没有"默认帮用户选中真实环境"的行为。

### 现状矩阵

"已实现"指代码路径存在；"验证"只算实际跑过的证据。"未支持"不是承诺，是当前缺口。

| 逻辑资产类型 | 设计要求（SPEC） | 已实现 | 验证 | 未支持 |
|---|---|---|---|---|
| 共享指令（instructions） | 软链、原生加载或 `@` 引用；版本、优先级、是否重复加载要验证 | `inventory` 发现用户级/项目级；`registry adopt/drift`；`release import/release/deploy` 三 Agent 软链；`change.py apply/status/restore` 与 `review-plan/review` | 沙箱：字节、链接、账本、逆序恢复；`examples/lightweight-loop` 按文档复跑（15 个 bash 块 exit 0，2026-10-31） | 真实 Host 是否加载与优先级；`@` 引用式部署（只有软链）；多 instructions 资产同时发布 |
| Skills | 共享目录软链或原生搜索路径；必须验证被发现和触发 | `inventory` 记 skill 目录、子目录、`SKILL.md` 指纹；`import` 整目录复制；release 逐文件 sha256；deploy 目录级软链 | 沙箱：skill 目录导入、发布、部署链接有测试 | `change.py` 不支持 skill（写死 `kind=instructions`、单文件 patch）；skill 的更新/复盘/撤销；发现与触发验证；`~/.agents/skills` 的 readers 是本机观察 |
| MCP | 统一逻辑 Catalog，按平台渲染；不覆盖未托管条目、不写密钥 | 把 `settings*.json`、`.mcp.json`、`mcp.json`、`config.toml` 当**文件**记 Hash 与顶层键名 | 盘点/漂移的文件级测试 | 条目级模型（server 标识、命令/URL、传输、启用状态）；渲染与合并；只记键名导致现在根本读不到条目，谈不上语义管理 |
| Hooks | 底层脚本共享，按平台包装；权限与事件语义差异 | `kind=hook` 枚举存在，但没有候选路径（hooks 写在 `settings.json` 里），盘点不会产出 hook 记录 | 无 | 事件模型、平台包装、加载验证 |
| 扩展 / 插件 / prompts / 子代理定义 | 底层脚本共享，按平台包装 | `inventory` 记录 `.pi/agent/extensions`、`.pi/agent/prompts`、`.claude/plugins`、`.claude/agents`、`.pi/agent/agents` 的一层条目 | 盘点有单测；发布部署未专门验证目录型条目 | `import` 只区分 skill（目录）与 instructions（文件），扩展/插件/prompt 没有导入与部署路径；启用状态；宿主加载规则 |
| 工具配置 / 权限 / 模型与版本 | 按平台探测工具与权限差异，不假定统一配置格式（SPEC §5 Adapter 原则） | `settings.json`、`config.toml` 只记 Hash 与顶层键名，不记值 | 无 | 值级模型、diff、版本引用；启用/禁用已安装工具的改动路径 |
| 项目级 Harness | `agent/project -> release` 绑定（SPEC §5 逻辑视图） | `inventory --project` 能发现项目级条目 | 盘点有单测 | 项目级部署与绑定（当前 `bindings.json` 只按 agent 记）、项目级漂移与恢复 |

会话历史不是资产，是证据来源：`history.py collect/group/digest` 已实现并做过真实只读运行，三家 Host 的格式表是本机观察、未按官方文档核实。它不是本矩阵的一行。

## 4. 证据口径

**三类信息分开标注，不能混用：**

- **用户明确偏好：** 来源是用户原话（带时间与位置），适用范围内有效；偏好变化时旧条目按“被替代”处理，保留历史与理由，不静默改写。偏好只描述用户明说的要求，不据此推断人格、性格或心理画像。
- **会话观察：** 来源是会话源文件指针；适用范围是该会话/项目，推广到别处需要新证据。
- **假设：** 本地没有证据，标"收益待验证"；文章和外部资料只是假设来源。

**来源与适用范围可修正：** 路径、时间、Host 与版本进入账本或报告；来源失效、Host 升级或依赖变化时标 `needs_review`，不沿用旧结论。

**不算改善证据的东西：** 用户批准、apply 成功、文件被写入、Host 没报错、"没人报问题"、检索没命中（`unavailable` 不等于 `no_match`，没命中也不等于问题不存在）。没有证据时复盘记 `observe` / `prediction_met=unknown`。

**评估层次沿用 SPEC §2.5：** L1（改动生效）能在沙箱完成；L2（隔离 Host 对照）和 L3（用户自己观察）需要隔离环境、真实 Host 运行和预算授权，只在用户点名、有争议或后果严重时做。本轮不运行 Host，也不把"还没跑 L2"写成"已验证"或"不可验证"。

## 5. 路线

四片按用户能感知的结果切分，不按技术层。每片自己端到端验收，不存在"最后统一集成"阶段。

### R1 独立开始使用

**用户场景：** 一个不是作者的用户在另一台机器上把仓库 clone 到任意目录，按文档在一个隔离目录里初始化自己的 PHE_HOME，看到"我有哪些 Harness 资产、来自哪个文件/软链、哪个 Host 入口在读、PHE 能管到哪一步"的发现报告。全程不改动他的 Host 配置。

**复用：** `tools/inventory.py`（候选路径表与分组）；`tools/registry.py` 的 `adopt`/`drift`；`release_deploy.py` 的守卫与 `sandbox_roots`；`tools/history_hosts.py` 的 Host 根解析；`examples/lightweight-loop` 的"每步命令 + 临时目录"写法。

**缺口与交付物：**

1. 初始化入口：创建/校验 PHE_HOME（目录骨架 + 版本标记），默认路径只在显式参数或环境变量下生效，不自动创建。
2. 发现报告：每类资产的来源路径、Host 入口、管理状态（可托管 / 仅观察 / 未支持）、加载链如实标 `unverified`。
3. 安装不依赖源码工作目录：入口能从仓库副本或安装目录运行，输出里没有开发者绝对路径。
4. 一份按文档可跑通的全流程，所有写入落在显式沙箱。

**验收：**

- 全新临时目录 + 仓库副本（不是开发工作目录）跑完整流程，`--home` 指向合成 Host 树，退出码 0。
- 发现报告覆盖 §3 的资产类型，每类都有管理状态；未知项不被写成"已支持"。
- 同一 fixture 两次运行输出一致（可复现）。
- 真实 `~/.pi`、`~/.codex`、`~/.claude`、`~/.phe` 前后 Hash 不变。
- 提交的工件里没有本机用户名和真实路径。

**依赖：** 无前置。与 R2/R3 共享契约：ObservedAsset 字段、`kind` 取值、PHE_HOME 目录骨架。

**完成 / 停止：** 上述五条全部通过并留可复跑工件即完成。需要真实 Host 加载验证或写真实 Host 目录时停下报批准，那不属于 R1 验收。

### R2 首条持续个性化闭环（指令）

**用户场景：** 用户在自己的 PHE_HOME（自己机器、仓库外）里：最近的 Pi 会话记录了他"回答先给结论"的偏好和两次越界叫停；生成本地摘要，宿主按指针回读核对，出一份逐条可审批的报告（三行说明 + 实际 diff）；用户只批准其中两条；应用后在新会话里复盘，对照原预测给出保留/调整/撤销；下一周期只处理新增证据，并读到上次的结论。

**复用：** `tools/history.py digest/collect/group`；`tools/change.py apply/status/restore/review-plan/review`；`tools/release*.py`；Skill §11–§13；`examples/lightweight-loop` 的命令串。

**缺口与交付物：**

1. 真实写入路径走通：在用户自己的 PHE_HOME 与入口上应用改动（现在只在临时 home 演练过；规则允许，流程没走过）。
2. 摘要 → 报告 → 变更包的衔接契约：报告必须带实际 diff 与三行说明，变更包必须引用当前报告的 sha256；缺项清单写清楚，不新增工具框架。
3. 跨次延续：账本要能支撑"只取上次复盘之后的新增证据"（`review-plan` 已给观察窗，增量取样由宿主按指针做，先用文档约束）。
4. 信息状态标注：报告与账本能区分偏好、观察、假设及来源范围（当前只有自由文本 `why`/`expected`/`verify`，先用文字约定与复核清单，不冻结新 schema）。
5. 用户可读的周期摘要：这轮改了什么、效果证据到哪一步、下次看什么。

**验收：**

- 在用户自己的隔离 PHE_HOME（非开发者电脑、非仓库目录）跑通一次完整环路：摘要 → 报告 → 逐条批准（`source=user`）→ apply → 新会话复盘 → 按结论 keep/adjust/revert；`revert` 经用户再次批准才 `restore`。
- 账本含 approval/apply/review 事实，三行说明原文入账；没有任何字段把批准或应用写成效果已验证。
- `restore` 能回到应用前字节。
- 第二次周期只引用第一次之后的新增证据，并能读回第一次的预测和结论。
- 没有 Host 加载或行为证据时，结论必须是 `unknown`，不得声称改善。

**为什么现在就能做：** 闭环代码已在沙箱跑通（`tests/test_change*.py`、`examples/lightweight-loop`），剩下的不是重新设计，而是进入用户环境与跨次延续。

**依赖：** R1（初始化、发现、入口路径）。共享契约同上。

**完成 / 停止：** 完成 = 一次用户环境闭环 + 一次跨次增量复盘，不要求量化收益。停止 = 用户没批准具体 diff/目标路径（真实写入必须逐条批准）；需要 Host 加载或行为验证但无预算授权时，该项标 blocked。**R2 完成不等于整个产品完成**：它只覆盖指令这一类资产和一个用户周期。

### R3 同一闭环扩到完整 Harness 资产

按资产类型逐条工作，每类有自己的缺口、验收和停止条件，不写"以后支持全部"。共同契约：`asset.json` 的 `kind`、`assets/<asset_id>/content/`、release manifest 的逐文件 sha256、`bindings.json` 的 agent → release 映射；新增一类只扩展类型和入口映射，不新建第二套布局。**工具不扩成任意软件包管理器**：不安装 CLI、不装依赖、不改系统环境，只管理用户已装工具的启用、配置和版本引用。

#### R3a Skills

**场景：** 用户的 6 个 Skill 散在 `~/.claude/skills` 和 `~/.agents/skills`（Codex 与 Pi 共享），其中一个总是触发不了。他想统一到一份逻辑源，改一次，并确认它真的会被发现和触发。

**现状：** 目录导入、逐文件发布、目录软链部署在沙箱有测试；`change.py` 不支持 skill。

**缺口与交付物：**

1. `change.py` 支持 skill 资产：多文件内容，patch 落到 `SKILL.md` 或引用文件。
2. skill 的更新、复盘、撤销走同一账本。
3. 共享目录 readers 的事实核实（`~/.agents/skills` 目前是本机观察）。
4. Skill 被发现/触发的 Host 层验证，单独一项。

**验收：** 沙箱 import 一个 skill → 部署到两个 Host 的 skill 目录 → 改 `SKILL.md` → apply → review → restore 回原字节，manifest 逐文件 sha256 前后一致；同一 skill 的两个入口指向同一发布，未托管的新 skill 不被覆盖。Host 层再加一项：隔离 Host 启动后的加载/触发证据（需预算批准，可后置，不冒充文件层通过）。

**依赖：** R1/R2 已在用的共享布局。与 R3b–e 无阻塞关系，可并行。

**完成 / 停止：** 文件层闭环 + 至少一次隔离 Host 的发现/触发证据即完成；没有预算授权时标 partial，不宣称触发有效。

#### R3b MCP

**场景：** 同一个 MCP server 在 Claude Code 和 Pi 各写一份配置，参数已经漂移。用户想维护一份逻辑定义、按平台渲染，不覆盖未托管的 server，也不碰密钥。

**现状：** 只按文件记 Hash 与顶层键名。

**缺口与交付物：** 条目级模型（server 标识、命令/URL、传输、启用状态；不含凭证值）；两份配置的识别与比对；渲染与合并规则（未托管条目不覆盖）；产物不含明文凭证。

**验收：** 沙箱两份 Host 配置各含 2 个 server（一个托管、一个未托管），渲染后托管条目一致、未托管条目字节不变、产物无凭证；drift 能报条目级差异；apply/review/restore 走同一账本。

**依赖：** 共享布局 + 多文件内容能力（与 R3a 同一机制）。契约可并行设计，集成时核对。

**完成 / 停止：** 上述验收通过即完成。读取凭证值、调用云服务、安装 server 都不在本路线。

#### R3c Hooks

**场景：** 用户的 hooks 写在 `settings.json` 里，想共享同一脚本给两个 Host、按平台包装事件，并且能看出"没生效"是配置错还是根本没被加载。

**现状：** 盘点不产出 hook 记录（无独立候选路径）。

**缺口与交付物：** hook 资产类型（脚本 + 平台事件映射）；与 `settings.json` 的托管边界（哪些键归 PHE）；加载/触发验证方法。

**验收：** 沙箱一个 hook 脚本被两个 Host 的配置引用并部署；改脚本 → apply → 恢复；文件层和加载层分开记录；真实触发需隔离 Host + 预算。

**依赖：** R3b 的配置条目模型。

**完成 / 停止：** 文件层 + 配置层通过即完成该切片；真实触发按预算另批。

#### R3d 扩展 / 插件 / 子代理与 prompt 定义

**场景：** Pi extension 和 `.claude/agents` 子代理定义散落，用户想统一版本，并知道什么时候被宿主的更新覆盖。

**现状：** 盘点有记录；发布部署未验证目录型条目。

**缺口与交付物：** 目录型资产的 import/release/deploy（多文件 + 目录链接语义；现在 `import` 把任何目录都归为 `skill`）；启用状态（extension 启停）；版本对照。

**验收：** 沙箱目录型资产部署、更新、恢复；条目级 sha256；未托管条目不覆盖。

**依赖：** R3a 的目录资产机制。

**完成 / 停止：** 沙箱闭环通过即完成；宿主加载规则另列验证项。

#### R3e 工具配置 / 权限 / 启用 / 版本

**场景：** Harness 里"允许哪些工具、什么权限模式、用哪个模型和 CLI 版本"分散在 `settings.json` 与 `config.toml`，改动会影响行为。用户想知道改了什么、下次是否还成立。

**现状：** 只记 Hash 与顶层键名，读不到值。

**缺口与交付物：** 值级配置项模型（白名单键）；工具启用/权限/模型/版本引用的 diff 与版本记录；来源范围（哪个 Host、哪个版本）入账。

**验收：** 沙箱两份配置改一条"启用/禁用已安装工具"，diff 可读、账本能复盘、恢复回原字节；不执行安装或升级。

**依赖：** R3b/R3c 的条目模型。

**完成 / 停止：** 上述验收通过即完成。不做软件包管理器，也不执行模型/CLI 升级。

### R4 多用户、多周期可持续维护

**用户场景：** 一个用户有两台机器（或两个用户各一台），各自 PHE_HOME；几个月后框架升级、偏好变了、Host 目录被手改。用户要的是"继续用，而不是推倒重来"。

**现状：** 账本、发布、绑定都在单个 PHE_HOME 下；没有跨实例隔离测试；没有框架升级兼容策略；外部变更只在 deploy 时中止并报告。

**缺口与交付物：**

1. 实例隔离：同机两个 PHE_HOME、两台机器的 PHE_HOME 互不读写；账本不把别人的绝对路径当永久证据。
2. 跨周期维护：新证据累积；偏好变化用"替代"而非静默改写；外部手改后用户选 `adopt / reconcile / leave_unmanaged`；框架升级后旧账本与绑定可读，或给出明确的兼容失败。
3. 退役与重开：Retired 账本，reopen 需要退役之后的新证据或用户显式授权。
4. 周期复盘视图：这轮改了什么、证据到哪、下次看什么。

**验收：** 同一台机器两个独立 PHE_HOME 互不影响（账本、发布、绑定）；旧版本账本在升级后被新版本读取并给出明确结果，不静默忽略；外部手改后 deploy 中止不覆盖，用户选择后继续；偏好被替代时保留历史与理由，不复用旧证据冒充新验证；产出一份真实周期复盘，含 `observe`/`unknown` 项。

**依赖：** R1–R3 的布局与账本；隔离核对可以先做，不依赖 R3 完成。

**完成 / 停止：** 上述验收在同一台机器的两个实例 + 一次升级路径上成立即完成。需要第二台机器或第二个真实用户时，须用户提供隔离环境；否则标 blocked，不伪造成完成。

**并行写入口径：** 同一工作目录同时只有一个写入者；并行工作各自用隔离工作树或独立临时目录，共享契约改动前先定字段。

**下一步（建议顺序）：**

4. 所有 Host 加载/触发验证统一走"一次性隔离 Host + 预算批准"，不和开发工作混在一起。

## 7. 完成口径与不做的事

- **完成状态必须带范围：** 写清哪一步在哪个环境验证过——文件层（沙箱字节/链接）、加载层（隔离 Host 确认被加载/触发）、行为层（观察窗或对照）。"沙箱通过"不等于"Host 已加载"，"Host 已加载"不等于"行为改善"。
- **沙箱是正常验收方式，不是临时妥协：** 项目测试、示例和每片验收都在临时目录里独立复现，不需要开发者电脑上的真实配置。涉及加载/触发的结论在一次性隔离 Host 里验证，同样不依赖开发者日常环境。
- **"接管开发者本机现有配置"（包括 temper 迁移）不是里程碑**，只是用户批准后可选执行的一次迁移任务，不进入任何 R 片的完成条件。
- **不加防御性工程任务：** 按 AGENTS.md 铁律，畸形输入、攻击防护、并发锁不列为交付项；出现时只记一行后续事项。
- **不做的产品扩展：** 不造 Agent/运行时，不做人格画像，不做评测平台化，不扩成软件包管理器，不建第二套任务账本或第二套资产布局。
