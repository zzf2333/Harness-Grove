# 已有方案的维护与再判断

## 目的与设计理由

Jianhe 帮助用户持续改善整套 AI 工作环境和使用方式。本入口回答：已经采用的方案，现在还值得保留吗？维护对象包括使用方法、配置、第三方工具和多 Agent 协作流程，不限于检查文件是否过时。

工具会更新，用户的任务和习惯会变化，原方案也可能增加新的交接和维护负担。因此要用后续证据检验当初的理由，主动研究相关能力的变化，必要时简化、替换或退出方案，不能只是不断修补旧配置。

使用宿主已有的读取、搜索、文档查询、编辑和执行能力，不依赖项目 CLI 或其他 Skill。保留有价值的做法，也接受原判断需要修正；没有观察机会时不强行给效果结论。

## 1. 开始任务并读回原决定

读取用户请求和本 Skill 后，按文末“两层记录约定”确定日志位置和可取得的本次宿主轨迹线索，尽早建立或续写 Markdown。只读材料按相关批次处理，读后及时记录实际覆盖、发现与未知项，再推进依赖这些结果的判断；不要求 Markdown 先于所有只读动作，也不允许到任务结束才补写全部过程。新一次维护引用原方案日志；同次任务继续原日志。

先按下方“事项续接约定”查看与本次范围相关的待跟进导航及后续日志，找回待观察、暂缓和待完成事项，不只看最近一份报告。读回每个原条目中的问题、目标、用户偏好、方案取舍、能力依据、适用条件、批准范围、实际改变、恢复方式与预期。用户点名某项时先聚焦它；要求全面维护时说明实际覆盖了哪些方案。

- 区分用户明确喜欢的做法、观察到的习惯和可能因限制产生的迁就。需求可能变化，不把旧观察永久固化。
- 没有旧记录时，从用户说明、现有内容和可获取的版本记录重建已知部分，缺失原理由就明确说明。普通配置不自动算作此前优化成果。
- 按批读取并记录已有用户环境总览和相关维护项说明，核对其中的内容源、宿主或项目入口、配置条目与实际流程；当前内容一致只说明现状一致，不能证明期间从未被修改。若现场与说明不同，先查清差异，不为符合文档覆盖用户改动。
- 复用原日志中的工作与能力认识，先检查哪些事实仍适用，再补影响本次判断的缺口，不重新调查所有工具。

## 2. 看后续工作与整套方案的表现

读取有关会话、任务结果和用户反馈，允许回看旧依据，不受新增会话扫描窗口限制。逐批记录来源、实际覆盖、观察与证据指针，未读和不可获取部分照实列出。区分用户交互、子代理、自动任务、演练与性质未知的材料；同一事件的继承或导出不重复计数，未知格式先核对宿主文档，不猜成真人行为。

围绕原目标判断：

- 是否出现过足以观察原预测的场景？结果、错误、操作往返或人工补救有何变化？
- 新方案是否增加上下文传递、等待、重复验证、学习、费用或维护负担？多个工具的交接与验收是否真的顺畅？
- 用户的任务、目标、约束或偏好是否改变？原方案是否仍适合现在的工作？
- 哪些成功经验有正面证据值得保留或推广，哪些内容重复、冲突或已经不再需要？

比较前回读原事项的观察口径与基线，按下方“指标与观察约定”核对来源、窗口、统计对象、单位/算法、有效机会和覆盖情况。没有原基线时保留原数据缺口，只报告当前观察，不反推改前结果。把基线与本期原始值、`n/N`（适用时）、证据位置、可比性及限制写在本次日志中，引用原条目，不改写原定义。

定义不同与条件变化分开处理：前者无法对齐就不算改善幅度；后者可以描述同口径观察值的变化，但不能直接归因于原优化。确认无相关机会时写不适用/未知，部分覆盖时只报告已观察样本；不能把缺失当零或把次数减少当比例下降。

没有投诉不等于有效，最近没触发不等于应该删除。区分配置在位、工具加载、流程可运行和实际收益。变化也可能来自任务、模型或其他因素，考虑反例和替代解释，不把同时发生当成因果证明。

## 3. 重新核对工具能力与替代做法

根据后续表现和环境变化，主动查相关工具的当前版本文档、帮助、变更信息和本地配置。区分宣称支持、该版本支持、当前可用和实际已用；原来必要的额外步骤或组件，可能已有更简单的替代。

从所需能力出发，也研究相关第三方方法与实践。官方资料说明支持条件，本地核对说明环境可用性，社区经验提供候选思路，三者都不直接证明对本用户有效。记录关键来源、版本、核对日期、适用条件和未知项，不凭记忆断言新版本能力。

比较维持原方案、调整现有用法、简化分工、合并重复内容、替换工具或退出方案，说明改变如何影响用户的工作结果与维护成本。不要因为有新版本就自动升级，也不要因为已经投入成本就继续维护不合适的方案。

资料不可获取时缩小结论，标出待核实项；外部检索不上传私人会话、配置或凭证。研究足以支持本次处置与下一步就停止，不遍历全部工具文档。影响执行的前提未核实时不进入依赖它的改动。

## 4. 给出处置并落实获准部分

每条判断串起：**原目标与理由 → 后续观察及能力变化 → 相关备选 → 为什么仍适合或不再适合 → 代价与未知项 → 下一步**，形成时及时写入日志。对涉及指标的条目，分别报告观察事实、可比性与限制、本期是否支持原预测、下一步处置；数值变化不自动产生保留、撤销或结项决定。

| 处置 | 依据 |
|---|---|
| 保留 | 仍符合需求，没有需要改变的依据；不代表效果已证实，也不排除继续观察 |
| 调整 | 目标、适用条件或实际表现变化，需要改变用法、配置或分工 |
| 精简或合并 | 存在明确重复或额外负担，简化后仍保留必要能力与约束 |
| 替换或退出 | 原方案不再适合，有依据选择替代方式或停止使用；说明切换与退出成本 |
| 删除或恢复 | 内容已被替代、不再需要，或需撤销具体改变；必须明确当前影响与恢复依据 |
| 继续观察 | 缺少观察机会或无法区分原因，写明需要什么证据，不强行修改 |

先展示具体差异、影响范围、方案切换的顺序与恢复办法。讨论处置不等于获得操作授权；恢复、安装第三方工具、权限变更、费用或部署都需要对应批准。已有明确且仍适用的批准可沿用。

获准后按下方“批准、应用与恢复约定”核对原事项、后续执行与当前内容，逐项实施。集中内容更新前确认所有引用入口的影响；原位配置只改批准条目；外部软件沿用原管理方式。已有成功记录且当前仍符合时不重做，不把没有执行证据的当前状态补写成历史应用。

用户要求恢复时，先比较原改前、实际改后和当前内容，准备只撤回原项的反向差异；其他内容后来被修改时保留它们。若原改动本身也被后续修改，或恢复依据不完整，则说明差异并暂停该项，不能整份覆盖。对应恢复批准仍有效时可沿用，不重复索取。实施前先记本次方案、批准与恢复依据，完成后核对真实结果并追加记录，不改变原历史。

需要重新设计方案时，可以带本次及原日志衔接 `harness-improve`；未安装它时，本入口也能在上述方法下比较方案并完成获准的维护，不要求用户重复背景。

## 5. 交付与更新认识

交付逐项处置、依据、实际完成情况、剩余未知、下一步观察与日志路径。用户应能看清整套工作方式为什么继续保留或怎样改变，而非只收到文件清理列表。

在登记、更新、退出或恢复等获准工作完成后，同步维护项说明中的核实现状、实际入口和维护方法，并更新用户根目录总览索引，注明仍未完成的部分。必要说明更新随工作完成，不额外反复申请批准；仅分析时不修改环境和资产说明，过程事项导航按下方续接约定处理。退出或删除内容不默认删除相关历史日志。

在本次日志追加更新后的工作与能力认识，链接原方案及其条目；保留旧预测和旧决定，不能事后改写成一直正确。记录里注明哪些新结论替代了旧判断，不新建另一套知识库或账本。

后续处置始终引用原事项链接，收尾把尚待决定、暂缓、待观察或待完成的内容和触发条件列入日志“待跟进”，并同步根 README 的对应导航。用户限制仅写日志时注明索引未同步，不能将索引缺项当已结束。只有有依据的决定才结束事项；未获得观察机会时继续保留未知。

未获取的来源不能推进其分析位置；维护时回读旧材料不冒充新增发现。用户明确要求清除私人记录时，按其指定范围处理。

完成意味着处置有依据、获准操作可核对且有恢复依据。保持现状或继续观察也是结果；没有行为证据时收益保持未知。

## 批准、应用与恢复约定

- 用原任务日志的条目链接定位建议，核对用户批准的目标、当前待改内容、具体改后内容或动作、影响范围、费用与恢复办法。批准记原话或会话位置，不能由 Agent 的判断、文档或工具输出产生。多条建议只执行获批部分；内容或影响实质变化时重新展示并取得对应批准，普通实施细节不反复询问。
- 实施前读原条目、后续执行记录和现场。已有成功记录且目标仍一致时说明已完成，不重复应用；当前已符合但没有执行证据时只报告“当前已符合”，不补造本产品执行历史。中断或状态不明时先查实际完成到哪里，不因缺少一条成功日志就重做。
- 对承诺可恢复的文件改动，先保存与本项操作对应的必要改前内容或可用版本引用，并读回确认能用；恢复依据放本次任务的 `backups/` 或记清已有版本位置，不覆盖以前的恢复依据，不把凭证值复制进说明。拿不到必要依据时说明缺口，暂停依赖它的改动。
- 将本次具体方案、批准来源与范围、核对后的恢复依据记入 Markdown 后，才执行对应配置或内容写入。按批准差异改实际内容源或条目，保留未涉及的其他内容；共享入口先确认影响范围，不因更新说明顺手应用其他建议。
- 每项操作后读回并比较实际结果，记录原内容、实际改后内容或差异、验证结果及未完成步骤。失败或部分完成如实记录，停止依赖失败步骤的后续写入；不自动重试、整包回滚或承诺跨文件事务。必要的维护说明与导航只反映实际完成部分，不把工具返回或预计结果提前写成成功。
- 恢复是独立获准的动作：引用原条目和具体执行，比较改前内容、当时实际改后内容、当前内容，提出针对当前内容的反向差异。已有明确恢复批准且前提仍成立可直接沿用；原应用批准不自动包含撤销、删除或额外安装。
- 只反转本项改动，保留后来发生的其他修改。受影响的同一内容也被改过、恢复依据不足或无法分清范围时，说明具体差异并暂停该项，不直接拿整份备份覆盖当前文件。恢复完成后读回、追加恢复事实和剩余差异，同步当前说明与导航，保留原预测、批准及历史记录；恢复不等于原方案已被证明无效。

## 指标与观察约定

- 只选与原事项目标和当前决定有关的指标，在该条目日志下记录观察口径、基线、后续结果和证据链接，不另建指标目录、数据库或重复账本。写明原预期方向和观察机会；偏好或清理可以定性核对，无基线也可提出获准试用，但收益保持未知。
- 口径包含需要的定义：统计对象（任务、调用、尝试等）、单位及算法或聚合方式、数据来源与位置、窗口和时区、纳入/排除与去重范围、实际覆盖及缺失、工具/模型/任务类型等相关条件。比例给分子和有效机会分母 `n/N`，次数不等于比例；耗时说明测量区间，费用说明来源。
- 完整观察、确认无机会、数据缺失或部分覆盖分开记录。`N=0` 是无观察机会，比例不适用、效果未知，不写成0%；分母未知不能计算比例。部分记录可报已观察样本的 `n/N`，同时写清缺口，不冒充全量结果。缺失的值不补零。
- 先核可比性再写变化。定义、单位或统计对象不同，先按已有数据对齐；无法对齐就并列展示，不算改善幅度。能识别可比子集时，说明选择理由、排除范围并保留原结果，不能事后挑选有利样本。定义相同但模型、任务构成或运行条件变化时，可描述观察值变化，但要注明比较限制，不直接归因于优化。
- 比较同时展示原始值和口径，说明是次数、比例还是其他统计量。用原始值复核实际采用的计算及附加解释，不写无助于当前决定的推算。不同条目的样本关系没有依据时，分别解释各自结果，不推断包含关系或合并统计。百分比与百分点不混用，不混比总计、均值和中位数。原口径、预测和基线保留；需要修正时追加原因及新口径，不重写历史来迎合结果。
- 涉及费用、Token 或耗时时才核对相应语义：账单金额、价格估算和余额变化分别标明，币种/计费范围不同不直接相加比较；没有计费依据不从Token推出实付。先分清累计与增量、缓存是否已包含、主子任务是否重复记录，避免重复累加。并行调用耗时之和不当作用户等待时间。
- 输出分开说明观察事实、可比性与限制、原预测在本期得到何种支持、下一步处置。即使同口径数值变好，也只是观察结果；配置应用、加载证据、其他变化及样本范围共同限制归因。无机会不算有效，数值变差不自动撤销，零失败不自动结项；需要继续观察的事项保留原链接与具体观察条件。

## 事项续接约定

- 每个建议或待处理观点以首次任务日志中的独立标题 `### P1` 等定位；链接指向该日志的 `#p1`。同一日志内不重用编号，后续任务继续引用原条目，不因换会话重新编号。新方案替代旧方案时才新建条目并写清关系。链接按当前文档所在目录解析，记录路径基准：根 README 引用原项可用 `logs/<原任务>/log.md#p1`，另一任务的日志应使用 `../<原任务>/log.md#p1`，不能照抄根目录的路径。
- 任务日志的“待跟进”部分列原条目链接、当前情况、理由、重评条件或下一步、最近相关日志；可用待决定、暂缓、待观察、待完成、已结束等普通文字。结束须有依据，不等于收益已证明，未批准不能记为已应用。
- 用户根目录 `README.md` 的“待跟进”一节仅作导航：链接事项，写一句当前情况与重评条件，指向最近相关日志。实际判断须回读原依据与后续决定，不把索引、文件修改时间或索引缺项当作事实证明；记录冲突时先核对，不猜哪份正确。
- 每次开始确定记录位置，按相关批次查看索引、原条目和后续日志并及时记录，再判断等待的条件是否出现。索引缺失、滞后或只写过日志时，按相关时间、来源和任务范围分批查看日志收尾，注明未覆盖范围；不默认通读全部历史，也不能说“索引没有所以不存在”。
- 常规使用包括写任务日志和更新“待跟进”导航，不授权改环境说明、资产或配置。根 README 尚不存在时，只按需建立这个过程索引，不臆造环境清单。用户明确只读或只允许写指定日志时遵守其限制；若连日志也不允许写，按日志约定暂停。
- 结束时在日志追加本次处理结果，更新对应索引链接和一句现状，不复制整段过程。无法或不允许同步索引时，将该缺口及待跟进事项写入日志并告知用户；下次须补查相关日志。已结束项可从待跟进导航移出，原条目与决定保留。交付前实际核对本次新增或修改的事项链接能找到目标文件和对应标题，不只检查路径文字。

## 维护内容约定

- 用户根目录默认是 macOS 的 `$HOME/.harness-grove/` 或 Windows 的 `%USERPROFILE%\.harness-grove\`，用户明确指定的整个根目录优先。其下 `README.md` 是用户环境总览，`assets/<有意义的名字>/README.md` 是每项维护说明，`logs/` 沿用任务日志；都在源码仓库外，按需要创建，不要求首次全量整理。
- 每项明确实际修改对象：集中维护的指令、完整 Skill、自写工具可放在该项目录中作为内容源；完整 Skill 放在 `skill/` 子目录并保留内部结构，宿主链接或原生引用须先核实支持。MCP 和其他宿主配置可留在原位置，这里只记文件、条目及负责修改的范围，不复制整份配置成为第二个来源。外部软件只登记来源、版本、位置、依赖与更新方法，沿用原管理方式，不复制程序。
- 每项说明包含：用途及为何使用、适用任务或项目、内容源和实际入口、怎样使用和修改、共享改动会影响谁、怎样核对与退出或恢复、关键资料的版本与核对日期、已确认和未知项、相关任务日志。示例必须标为示例；凭证只记已有安全来源或引用方式，不复制值。
- 根目录总览写当前工具分工、工作流程和维护项索引，并提供“待跟进”导航；链接各项说明和任务日志，不重复详细状态；流程确实较长时才按需拆分说明。内容和说明代表核实后的当前情况，操作与历史理由留在日志中，恢复副本仍使用任务目录的 `backups/`。
- 用户只要求分析时不建立维护项或修改总览中的环境与资产说明；过程事项导航按上述续接约定更新。批准登记或实施后，必要的说明更新随对应工作完成，不重复申请审批；记录现状不等于批准接管，更不代表已安装或加载。迁移、链接和配置调整须说明具体路径及所有受影响入口，按对应批准执行。
- 现场与说明不一致时先查清实际情况、解释差异，不为符合文档覆盖用户修改；按实际完成范围更新说明，未完成或未核实的内容明确标注。单独指定日志位置不改变内容目录，不自动迁移已有内容；三个入口沿用同一份总览和维护项，不另建数据库或账本。

## 两层记录约定

- 宿主原生轨迹用于核对实际操作，Markdown 用于记录证据、判断、批准、结果和恢复依据，两者不能互相替代。在 Markdown 中记录已确认的 Host、本次会话或运行标识、轨迹路径或导出引用、实际核对范围及已知留存条件；不明就写未知。
- 轨迹位置必须核对确实属于本次运行。只查看必要元信息与工具调用、结果，不复制整份会话、凭证或内部逐字推理。路径存在不证明记录完整，当前可读不保证长期保留；不能取得或读回时明确缺口，不猜路径、不把事后说明冒充原生轨迹，也不自动打开宿主日志设置。由他人提供的证据注明提供者和核对范围。

- 每次任务使用一份 Markdown 日志。默认日志根目录：macOS 为 `$HOME/.harness-grove/logs/`，Windows 为 `%USERPROFILE%\.harness-grove\logs\`（PowerShell 用 `$env:USERPROFILE` 读取用户目录）。由宿主解析成实际绝对路径，不硬编码磁盘、用户名，也不把环境变量占位符当目录名。用户明确指定整个用户根目录时，默认日志改用该根目录下的 `logs/`；下述明确日志位置和接续规则仍优先。
- 位置优先级：用户本次明确指定的位置 → 接续任务的原日志 → 用户已明确设置的保存位置 → 默认目录。旧日志的位置不自动成为永久设置。使用默认目录无需例行询问；无法确定用户目录或不能写入时才说明原因并请求可用位置。用户拒绝保存时暂停，不静默改用聊天记录。
- 新任务由宿主创建 `YYYYMMDD-HHmmss-入口名/log.md`，例如 `20261103-143000-harness-review/log.md`；使用本机开始时间，日志内注明可获取的时区，不编造时间。名称不含冒号，同名的新任务加 `-2` 等后缀，不覆盖旧任务。需要改前副本时才在该任务目录创建 `backups/`。告知用户实际日志路径，不需要初始化命令，不自动迁移旧日志。
- Markdown 尽早建立，未知信息记“待查”。允许只读材料按批读取后及时记录实际覆盖和观察，随后再形成或记录依赖这些观察的判断；补记写明真实顺序，不把后来知道的信息伪装成启动时已知。不能将整个任务的操作和理由都拖到结束才补写。
- 同一次任务跨 Skill 共用原 `log.md`，不因切换入口重命名目录；接手先读已有进度、依据和批准。后续新任务另建任务目录并链接原日志，保留原结论，不覆盖原预测。相对路径以当前日志所在的任务目录为基准并在日志中说明；外部证据注明来源和具体位置，不假设换电脑后原路径仍可用。
- 按发生顺序及时追加，每条用序号或可获得的时间标识，记目的、对象、实际动作和结果。相关读取、搜索可合并为一批，但须列清来源和实际覆盖；日志写入本身不用递归记录。
- 重要判断记录证据、相关备选方案、选择理由、代价和未知项，作为可审阅的决策说明，不记录模型内部逐字推理。补记注明补记，遗漏注明缺失，不编造当时的依据。
- 修改配置、资产内容或安装工具等改变之前，必须在 Markdown 记下具体方案、用户批准原话或会话位置、批准范围和恢复依据；执行后及时记录实际差异、结果与验证。只读批次补记不放宽这条写入边界。过程索引的更新仍按事项续接授权记录实际结果，日志和索引写入不需要递归记日志。Agent 自己写下“批准”不产生授权。不覆盖用户已有修改；共享入口与既有管理方式的影响须核对。恢复也需要对应批准。
- 写入失败时暂停新的正式分析和配置修改，只做必要的只读核对并报告实际状态；不自动换目录、重做操作或回滚。恢复记录能力后，先补明状态再继续。用户叫停时先停止工作，再报告已知状态。
- 只存必要摘录、来源指针和恢复依据，不复制整份私人会话或凭证。用户数据不进入项目源码仓库。演练材料、批准与结果明确标为合成，不冒充真实用户授权。
