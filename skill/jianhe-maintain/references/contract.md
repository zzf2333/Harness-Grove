# 用户核心、跨工具投影与操作契约

本参考定义 Jianhe `v0.0.4` 的四层用户数据模型、有界 RSI 收敛规则、两层记录、精确批准与三方恢复、以及收益与归因口径。三个 Skill 目录随包携带相同副本，不依赖项目 CLI、守护进程、数据库或其他 Skill 安装状态。

## 1. 用户根目录与四层对象模型

用户根目录默认位于用户主目录下的 `.jianhe/`：macOS 为 `$HOME/.jianhe/`，Windows 为 `%USERPROFILE%\.jianhe\`（PowerShell 用 `$env:USERPROFILE` 解析实际绝对路径，不硬编码盘符或用户名，也不把环境变量占位符当目录名）。

- 用户明确指定整个用户根目录时，新内容默认写入该指定根目录；仅指定本次日志路径只影响日志，不改变内容目录。已有内容不自动迁移，各目录按需创建，不要求首次全量盘点环境。用户数据绝不进入项目源码仓库。
- 四个组成部分各司其职，普通项目开发任务直接读取宿主原位指令或配置，**不读取 `.jianhe/` 目录**：
  1. `CORE.md`：**用户内在核心（唯一权威）**——承载经用户确认的目标排序、判断品味、领域工作法、授权与注意力边界，另设隔离的“待确认候选”与“工具迁就清单”。
  2. `README.md`：**全局导航与有界 RSI 看板**——维护项索引、`在验证` 与 `待决定` 双池看板、下次建议复盘日期。
  3. `assets/<名字>/README.md`：**工具层投影与维护说明**——说明如何把已确认核心投射到各 Agent 指令、Skill、配置或外部工具组合，并维护溯源映射表。
  4. `logs/<任务>/log.md`：**两层记录与恢复依据**——按批记录证据、判断、批准范围、实际差异，以及按需保存在 `backups/` 的改前副本。

### 1.1 一等公民：`CORE.md` 规范与状态流转

人是唯一主体，Agent 工具只是围绕用户核心存在的可替换执行器。`CORE.md` 按以下结构组织：

```markdown
# 用户内在核心（Jianhe CORE）
> 仅“已确认”条目生效并可投影至工具配置；“待确认候选”与“工具迁就清单”不作为自动执行依据。
> 最近确认：YYYY-MM-DD

## 1. 目标与价值排序
### C1 <用用户原话或直白工作语言陈述一句话准则>
- 来源类型：明示偏好 | 观察习惯
- 状态：已确认（YYYY-MM-DD，确认位置：logs/.../log.md#c1 或会话标识）
- 证据依据：<用户原话位置，或 ≥2 个独立工作事件指针>
- 当前投影：assets/<名字>/README.md#映射（尚未落地写“未投影”）
- 适用范围：全局 | <特定项目或任务类型>

## 2. 判断品味与完成标准
## 3. 领域工作法
## 4. 信任、授权边界与注意力分配

## 待确认候选（未确认前不生效、不投影）
### C7 <候选工作要求转述>
- 来源类型：明示待核 | 观察习惯（≥2 独立事件）
- 证据与提出：YYYY-MM-DD · <宿主/会话标识或日志指针>
- 状态：候选待确认 | 已拒绝（简记不采纳原因，避免后续重复提议）

## 工具迁就清单（消除目标，不属于核心偏好）
### A1 <因工具或流程限制被迫重复的绕行动作>
- 受限原因：<工具/配置缺口；未核实标“推测”>
- 消除方向：<一句话方向> · 关联事项：<看板链接或“待立项”>
- 状态：待消除 | 验证中 | 已消除（附观察证据） | 改判为偏好（转入 C 候选待确认）
```

核心条目统一使用 `C1`、`C2` 等全局递增编号（从候选转为确认时保持原编号不变，已拒绝或已撤回编号不重用），工具迁就统一使用 `A1`、`A2` 等全局递增编号。严格遵守以下 6 条硬约束：

1. **禁止黑盒心理推断**：每条只写可观察的工作要求（目标取舍、质量标准、拆解与验收方法、权限与精力分配），严禁推断人格、性格、情绪、动机或私人标签。
2. **独立证据门槛**：“观察习惯”须有至少 2 个跨轮或跨会话的独立工作事件指针才能提议为候选；单次观察只记入当次任务日志。
3. **唯一确认生效路径**：未经用户同意不新建或改写 `CORE.md`（未表态或仅做只读分析时，提炼结果只记入当次 `log.md`）。只有用户本人对具体措辞明确确认后，条目才能写入正文四节并向下游投影（对话中明确要求“记住 X / 以后一律 X”视同确认该原意）；用户同意暂存待核或记录拒绝防重提时，才写入“待确认候选”或“`A<n>` 工具迁就清单”。候选条目、已拒绝条目与 `A<n>` 迁就条目严禁投影进宿主配置或作为自动执行依据。
4. **迁就不入核心**：因当前工具缺失、上下文断裂或接口笨拙而产生的重复手工补救归入 `A<n>` 作为待消除靶子，绝不当成“用户习惯”写进指令永久固化。若用户明确表示“我就喜欢亲自做这一步”，再转入 `C` 候选确认。
5. **容量防膨胀与退役移出**：正文每节建议不超过 7 条已确认核心，候选区不超过 10 条；超出时优先合并提炼或请用户裁剪。已确认核心因目标或环境变化经用户确认`已撤回`时，从正文移出（在当次 `log.md` 保留原条文与撤回原因，并同步检查下游投影），不让 `CORE.md` 沦为第二本流水账。
6. **用户直接编辑优先与可恢复**：用户可随时手改或删减 `CORE.md`。Jianhe 每次读取以当前文件内容为准并核对下游投影是否需同步，绝不用旧日志覆盖用户手改；获准修改已有 `CORE.md` 前同样先核对现场并保存改前恢复依据。

### 1.2 工具层投影（`assets/`）与双向对齐

每个维护项使用有意义的目录名，按实际修改对象采用对应维护方式，不为了目录整齐而复制全部配置：

| 维护方式 | 实际修改对象与边界 |
| --- | --- |
| 集中内容源 | 共享指令（如 `AGENTS.md`）、完整 Skill（放 `skill/` 子目录并保留内部结构）、自写工具在 `assets/<名字>/` 保存内容源。各宿主用已核实支持的链接或原生引用接入；更新前说明所有受影响入口，不假定共享文件天然跨宿主兼容 |
| 原位配置说明 | MCP、权限和其他宿主配置仍留在原配置文件中。`README.md` 只记录文件、条目、负责修改的范围与方法，不复制整份配置成为第二个来源 |
| 外部工具登记 | 由外部包管理器或安装器管理的软件只记用途、安装来源、版本、位置、依赖与更新方法，沿用原管理方式，不复制程序 |

每项 `assets/<名字>/README.md` 包含：用途与理由、适用任务或项目、内容源或实际修改入口、**核心投影映射表**、共享更新影响谁、核对与退出/恢复方法、关键资料版本与核对日期、已确认与未知项、相关任务日志。配置示例必须标明是示例，不能当作现场覆盖配置；凭证只记已有安全来源或引用方式，绝不复制凭证值。

映射表至少记录：`来源锚点（C<n> / A<n>消除 / —） | 目标宿主文件与章节 | 投影内容摘要 | 更新日期 | 性质（核心投影 | 迁就消除方案 | 工具局部适配）`。

- **机制保证什么、不保证什么**：保证每处受管内容都能回答“服务哪条已确认核心、消除哪条迁就，还是纯工具局部适配”，每次 `review` / `maintain` 核对现场漂移，所有修改走具体批准与恢复依据；它**不是自动编译器或后台同步进程**，不保证实时检测，不保证宿主已重载生效，也不保证不同宿主对同一自然语言规则的执行力一致。
- **登记不等于接管**：只要求分析时不顺手建维护项或修改总览中的环境与资产说明；批准登记或实施后，必要的说明和总览同步包含在对应获准工作中，无需重复申请审批；迁移、建链接和改宿主配置仍须具体批准。
- **双向漂移核查与对齐**（按具体差异片段按序判定，发现现场与映射/说明不一致时先查清事实，绝不为符合文档覆盖用户手改）：
  1. **双端同时修改冲突（最高优先）**：同一语义在 `CORE.md` 与宿主现场均发生独立修改 → 保留两端原貌，标为“双端冲突待决”并列展示差异询问用户，绝不单向覆盖；
  2. **单向宿主手改（通用要求）**：仅宿主侧新增或修改跨工具通用的目标、标准或工作法 → `review` / `maintain` 提议**反向吸收**进 `CORE.md`（生成候选或修订提议），经用户确认后再按需同步其他宿主投影，原手改保留；
  3. **单向宿主手改（局部参数）**：仅涉及单一宿主的模型路由、额度参数或专属工具语法 → 在映射表中更新登记为“工具局部适配”，不回写 `CORE.md`；
  4. **单向核心已变而投影滞后 / 未确认泄漏**：仅 `CORE.md` 已修订或撤回而下游投影未同步，或投影混入未确认候选 → 列出差异，获批后更新或清理（`v0.0.3` 遗留的“历史未溯源”内容先按第 2/3 条做反向吸收或局部适配归类，不因未溯源直接提议删除）；
  5. **意图不明** → 标为“漂移待决”集中询问一句，未决前不改宿主文件。

### 1.3 有界 RSI 看板与跨会话事项续接（根 `README.md`）

每个优化建议或待处理事项以首次任务日志中的独立标题 `### P1`、`### P2` 等为唯一身份；同一日志内不重用编号，跨会话始终引用原日志 `#p1`，只有新方案替代旧方案时才新建条目并写明替代关系。相对路径按当前文档所在目录解析并注明基准：根 `README.md` 引用 `logs/<原任务>/log.md#p1`，另一任务日志引用 `../<原任务>/log.md#p1`，交付前须实际核对目标文件与标题存在。

根 `README.md` 维护双池有界看板与下次建议复盘日：

- **默认在制上限（WIP）**：`在验证` 上限 **5 项**（已获批落地、待真实工作检验），`待决定` 上限 **5 项**（已识别机会或暂缓候选）。用户可按自身节奏显式调整上限并记入根 `README.md`。
- **`在验证` 入池四要素（缺一不可）**：
  1. **服务锚点**：对应已确认的 `C<n>` 或待消除的 `A<n>`（无锚点的纯工具折腾禁止入池）；
  2. **用户可感知正信号**：用户本人能直接体会的改善（如减少打断、减少重复背景解释或手工修补、提升一次验收通过率），严禁用“文件写入/加载成功”冒充；
  3. **代价与反向信号**：出现什么现象说明增加了等待、交接或维护负担；
  4. **到期条件**：默认 **30 天或 3 次相关真实任务**（先到为准）。
- **满额门禁、豁免与容量归属（禁止池外影子清单、自动扩容或静默淘汰旧项）**：
  - 当 `在验证` 已满上限时，**阻塞一切新增复杂度的方案**（新规则、新角色、新脚本、新第三方工具），须先结算旧事项腾出容量；**纯删减精简、故障修复、三方恢复、漂移对齐及 `CORE.md` 候选确认/拒绝豁免实施门禁**。
  - **所有活跃事项必须计入对应池上限，不在根 `README.md` 另建池外暂存区**：纯删减、三方恢复、漂移对齐及 `CORE.md` 确认无需跨任务观察，不占 `在验证` 槽位（撤回原在验证项则直接结项释放槽位）；对已在池事项的故障修复归入原 `P<n>` 观察记录，不增占槽位；确需**独立跨任务观察**的紧急故障修复，获批实施时**必须即刻在本次 `log.md` 写全四要素并从实施当刻起算到期条件**，入看板时须由用户同步结算一项旧项腾位，或由用户显式批准上调上限（严禁挂在池外延后计时）。
  - **`待决定` 满额处置**：当 `待决定` 已满上限时，新识别机会仅作为**未激活历史观察**记入本次 `log.md`（生成 `### P<n>` 供后续按日志检索），不自动扩容、不自动淘汰旧项，也不在根 `README.md` 追加池外活跃指针；向用户并列展示新机会与当前 `待决定` 清单，仅在用户明确放弃/合并旧项腾位或显式上调上限后才进入活跃看板。
- **到期强制收敛**：到期且已有相关任务机会但无正向用户收益证据（或长期零触发且存在维护负担）的复杂机制，`maintain` 默认提议**精简或撤回**；仅在确认尚无观察机会或关键外部变化干扰判断时，写明具体条件**最多延期一次**。“已结束”须有明确依据（毕业留存、撤回、放弃或被替代），不等于证明有效；未获批事项不得记为已应用。
- **续接与索引缺失补查**：任务收尾在日志“待跟进”列出活跃事项的原条目链接、现状、理由、重评或到期条件及最近相关日志，并在双池上限内同步根 `README.md` 看板（已结束项移出活跃池，未激活的超额历史机会仅留原日志备查；根 `README.md` 尚不存在时可只建立看板索引，不臆造环境清单）。用户明确限制只读或仅写指定日志时遵守限制，在日志注明看板未同步并告知用户；下次启动时按相关时间、来源与任务范围分批补查日志收尾，不默认通读全部历史，也不因看板缺项断言“无待办”。记录冲突时回读原依据与后续决定核实。

### 1.4 投影轻约定（可选接入，未触发时零用户根目录读写）

经用户单独批准后，可将以下轻约定写入共享 `AGENTS.md`（安装时填入当前 `<YYYY-MM-DD>` 下次建议复盘日，展示替换后全文供用户批准）。约定只做实时识别与收尾确认，**自身不读写用户根目录，不承载任何写入或备份流程**；所有落盘只经 Jianhe Skill 按本契约第 1.1、2、3 节执行。

```markdown
## Jianhe 协同轻约定
- 普通项目任务按本文已有规则工作，不读取、不写入 Jianhe 用户目录。
- 用户明确要求“记住/以后都/别再…”，或同一会话内对同一方向连续纠偏两次时：在当前任务收尾用一句话转述该工作要求，问用户是否记为 Jianhe 候选。用户同意后，若当前可调用 `jianhe-improve` 或 `jianhe-review` 且用户愿意现在处理，就交由该 Skill 落盘；否则只在回复末尾单独输出一行：`[Jianhe 待落盘] <YYYY-MM-DD> · <明示要求|同向纠偏×2> · <用户原话或转述，不含凭证>`，留待下次 Jianhe 复盘处理。用户未同意则不输出。
- 用户主动讨论工作流或环境优化，且当前日期晚于 `<YYYY-MM-DD>` 时：提醒一句有到期观察项，可用 `jianhe-maintain` 结算。
```

- **保证什么**：日常会话不因本约定读写用户根目录；`CORE.md` 只有一条写入路径，即 Jianhe Skill 加完整写入门禁。
- **不保证什么**：`[Jianhe 待落盘]` 行只是会话里的线索，不是记录，也不是日志。它能否在下次复盘被读到，取决于宿主会话的留存情况，以及 `jianhe-review` 本次实际读取的范围；会话丢失时，这条线索随之丢失。不同宿主对这段自然语言的执行程度也可能不同。
- **授权含义**：锚点所在会话位置，可作为“追加到待确认候选”的批准依据。写入正文四节仍按 1.1 第 3 条，在 Jianhe 会话中确认具体措辞。

请求批准接入时，向用户说明：本约定只让宿主在收尾询问，并输出单行锚点或转交 Jianhe Skill，不授予日常会话任何文件写入权限。以后更新复盘日期或约定文本，仍属于宿主文件修改，需要对应批准。

### 1.5 新用户与 `v0.0.3` 老目录的渐进升级

- **全新用户（无 `.jianhe/`）**：首次调用按需建立本次 `logs/`；产生候选或获确认时才建立 `CORE.md`，不要求预先填写环境清单。尚无已确认核心时，`improve` 先帮用户从当前诉求提炼候选并确认，或将方案明确标为“核心依据待确认”。
- **`v0.0.3` 已有目录（有旧“待跟进”、`assets/`、`logs/`，无 `CORE.md`）**：不强制一次性迁移，不删除任何旧记录。原“待跟进”保留在 `### 旧版待跟进（待分诊）` 区（不计入 5+5 上限，不再接收新项，分诊前不直接扩建实施）；现有资产映射暂标“历史未溯源”。由 `review` / `improve` 从既有共享指令和日志中提炼首批 `CORE.md` 候选供用户确认，由 `maintain` 分批将旧 `P` 项分诊归入 `在验证`、`待决定` 或结束。

## 2. 两层记录与任务日志约定

- **两层互补**：宿主原生轨迹用于核对实际工具调用与结果，Markdown 日志用于记录证据、判断、批准、结果与恢复依据，两者互不替代。在 Markdown 中注明已确认的 Host、本次会话或运行标识、轨迹路径或导出引用、实际核对范围及已知留存条件；不明写未知。
- **原生轨迹核实边界**：轨迹位置须核对确属本次运行。只查看必要元信息与工具调用/结果，不复制整份会话、凭证或模型内部逐字推理。路径存在不证明记录完整，当前可读不保证长期留存；不可获取时明确缺口，不猜路径、不用事后说明冒充原生轨迹，也不自动开启宿主日志设置。他人提供的轨迹证据注明提供者与核对范围。
- **日志位置优先级**：**本次明确指定的位置 → 接续任务的原日志 → 用户已明确设置的保存位置 → 默认目录（`.jianhe/logs/`）**。发现旧日志不代表该路径是永久设置；使用默认目录无需例行询问，无法确定用户目录或无法写入时说明原因并询问可用位置；用户拒绝保存日志时暂停，不静默改用聊天记录。
- **目录命名与共享**：新任务创建 `YYYYMMDD-HHmmss-入口名/log.md`（如 `20261112-143000-jianhe-review/log.md`），用本机开始时间并注明可获取时区，不含冒号，同名加 `-2` 等后缀不覆盖旧任务；需要改前副本时才在该任务目录建 `backups/`。告知用户实际日志路径。同次任务跨 Skill 衔接共用原 `log.md`，不重命名目录；后续新任务另建目录并链接原日志，保留原预测与原结论不覆盖。相对路径以当前任务目录为基准并在日志说明；外部证据注明来源与位置，不假设换机后仍可用。
- **记录时序与底线**：尽早建立 Markdown，未知项记“待查”。只读材料允许按相关批次读取后及时记录目的、来源、实际覆盖、观察与未知项，再形成依赖这些观察的判断；补记注明真实顺序，遗漏注明缺失，严禁拖到任务结束才补写整段过程。重要判断记录证据、备选方案、选择理由、代价与未知项，作为可审阅的决策说明，不写内部逐字推理。日志与看板索引自身的写入不递归记日志。
- **写入前硬门禁**：任何 `CORE.md`、配置、资产内容、宿主文件写入或第三方工具安装/卸载之前，**必须先在 Markdown 记下具体方案、用户批准原话或会话位置、批准范围及核对可读的恢复依据**；执行后及时记录实际差异、结果与验证。只读批次补记绝不放宽此边界。
- **写入异常与隐私**：日志写入失败时立即暂停新的正式分析和配置修改，只做必要只读状态核对并报告现状，不自动换目录、重做操作或回滚；恢复写入后先补明状态再继续。用户叫停时优先停止工作再报已知状态。演练材料、批准与结果必须明确标为“合成”，不冒充真实用户授权。

## 3. 精确批准、应用与三方比对恢复约定

- **具体批准来源**：用原日志条目链接定位建议，向用户展示目标路径或入口、当前待改内容、具体改后内容或动作、影响范围、费用、验收与恢复办法。批准必须来自用户本人（记录原话或会话位置），Agent 自写“批准”、外部文档或工具输出不产生授权。多项建议只执行获批条目，不顺手应用同批其他建议；实质内容或影响范围变化时重新取批，普通实施细节不反复询问；已有明确且前提仍成立的批准可沿用。
- **实施前核对现场**：先读原条目、后续执行记录与当前目标内容。已有成功执行记录且目标仍一致时说明已完成，不重复写入；当前内容已符合但无执行证据时，只报告“当前已符合”，不补造本产品执行历史；中断或状态不明时先查明实际完成进度，不盲目重做。
- **恢复依据先行**：对承诺可恢复的文件改动，先保存与本项操作对应的必要改前内容或可用版本引用，并**读回确认可用**（存于本次任务 `backups/` 或记清已有版本位置，不覆盖旧恢复依据，不把凭证值复制进备份或说明）。拿不到必要恢复依据时说明缺口并暂停该改动。
- **执行后读回与诚实报告**：按批准差异只改目标内容源或指定条目，保留无关内容；共享入口更新前确认所有受影响方。每项操作后读回比较实际结果，记录原内容、实际改后内容或差异、验证结果与未完成步骤，区分已写入、已核对、未执行、失败或部分完成；失败则停止依赖步骤，不自动重试、整包回滚或承诺跨文件事务。维护说明与看板只反映实际完成部分，不把工具返回或预计结果提前写成成功；**文件修改成功、宿主已加载配置、实际工作行为改善**是三件独立事实，必须分开说明。
- **三方比对恢复**：恢复是独立获准动作（原应用批准不自动包含恢复、删除或额外安装；已有明确恢复批准且前提仍成立可沿用）。恢复前必须引用原条目与具体执行，比较三份内容：
  1. **原改前内容**：确认修改前原本是什么；
  2. **当时实际改后内容或差异**：确认本项操作究竟改了哪几处；
  3. **当前现场内容**：识别后来发生的新修改，生成**只撤回本项改动的反向差异**并完整保留后续其他修改。
  若受影响的同一片段后来也被修改、恢复依据不足或边界不清，必须说明具体差异并暂停该项，**严禁拿整份旧备份直接覆盖当前文件**。恢复完成后读回核实、追加恢复事实、同步说明与看板，保留原预测和历史记录；恢复本身不等于证明原方案无效。

## 4. 用户收益、指标口径与归因约定

- **服务于人的体验与目标**：评估优先看用户可感知的工作结果与心智负担变化（如是否减少方向纠偏、减少跨工具手工搬运、减少无意义打断、提升一次交付可用度），在原事项及后续日志中记录观察方式、基线与证据，不另建指标目录、数据库或仪表盘。偏好对齐、流程理顺与冗余清理可定性核对；无历史基线也可提出获准试用，但未观察前收益必须标为未知，不事后补造改前数值。
- **定量口径可复核**：涉及数值比较时写清统计对象（任务、请求、尝试等）、单位与算法/聚合方式、来源与位置、窗口与时区、纳入/排除与去重范围、实际覆盖与缺失、工具/模型/任务类型条件。比例同时给出分子与有效观察机会分母 `n/N`；次数不等于比例，百分比与百分点不混用，不混比总计、均值与中位数；耗时说明测量区间，费用说明来源。
- **区分无机会与缺失**：完整观察、确认无相关任务机会、数据缺失、部分覆盖四者分开记录。`N=0` 表示无观察机会，比例不适用、效果保持未知，严禁写成 `0%` 或据此宣称有效；分母未知不算比例，缺失数据不补零；部分覆盖可报告已观察样本的 `n/N` 并同时写明缺口，不冒充全量。
- **先核可比性，再谈归因**：定义、单位或统计对象不同时，能从原始数据对齐才比较，否则并列展示、不算改善幅度。使用可比子集须说明选择理由、排除范围并保留全量原结果，不能事后挑选有利样本。定义相同但模型、任务构成或环境条件已变化时，可描述观察值变化并注明比较限制，不直接归因于原优化。不同条目的样本包含关系未知时分别解释，不自行合并或跨条目推算；用原始值复核实际计算，原口径、预测与基线保留不改写（修正口径需追加说明）。
- **费用、Token 与耗时语义**：仅在与目标相关时核对。账单实付、单价估算与余额变化分别标明，币种或计费范围不同不直接相加，无计费依据不从 Token 推导实付费用；先分清累计与增量、缓存是否包含在内、主会话与子代理是否重复计入，防止重复累加；并行调用耗时之和不当作用户实际等待时间。
- **四段式维护输出**：涉及观察比较时，分别陈述**观察事实 → 可比性与限制 → 本期对原预测的支持程度 → 下一步处置**。同口径数值变好也只是观察事实，仍受加载证据、并发变化与样本量限制；无观察机会不算有效，数值短期波动不自动触发未获批撤销，零报错/零失败不自动结项。
